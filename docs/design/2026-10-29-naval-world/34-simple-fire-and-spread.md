# 一键救火与首／中／尾渐进蔓延 · 设计提案

2026-10-29。**H5 独立纯核、原 Demo 三区扩展与连续 GPU 已验证；正式游戏、真实命中分区和存档接线未完成。** 最新交付见37号记录，GPU为zones-gpu-02（350PNG／334样本／3960步）。以下规则和接受项保留提案过程，完成范围以最新交付为准；旧单热区GPU不替代新候选证据。

## 玩家目标与取舍

目标体验是命中处起火、邻近甲板逐渐受威胁，玩家按一次“扑救火灾”，船员自动处理本次火情；玩家继续操船、交战或撤退。固定4人属于后台命令，普通HUD不让玩家选人数。正式单按钮界面按36号记录验证；分区已有37号独立画面，正式命中接线仍待完成。借鉴《要塞十字军》的自动劳动感觉，不声称复现内部算法或复制素材。

**决策修订 H5：先验证更小的独立原型。** 原稿曾提出持续自动政策开关、1..3 人自动派遣、三区内分段热率分配与独立 r2 热学核；均未实现，现从本候选移除。锁定以既有 r1 核作为唯一热量积分／燃料／工作／DOT 内核，r2 仅记录粗粒度热量份额和邻区暴露计数。每个火情使用现有派 4 人命令与原自动返回规则；跨火情自动重派、储备耗尽自动撤回和新 UI 尚未纳入 H5。

本提案选择三热区：船首 `bow`、船中 `mid`、船尾 `stern`，邻接仅为首—中—尾。三者是游戏空间抽象，不称真实水密舱、逐木板热学或历史防火分区。风、帆索传播、跨船引燃、烟幕遮视、火药殉爆与火致货物损失均不在本候选内。

| 方案 | 能表达什么 | 状态、成本与问题 | 本轮决定 |
| --- | --- | --- | --- |
| 只将旧单火点扩成更多火焰 | 画面面积变大 | 不能让扑灭某处阻断邻区引燃；无法给出真实局部状态 | 保留为视觉基线，不算蔓延 |
| 首／中／尾三热区 | 命中区起火、相邻扩展、自动压制局部火源 | 固定 3 区、2 条邻接边；便于保存、暂停、回放与数值对照 | 推荐的最小权威模型 |
| 逐木板／细网格 | 更细的材质与路径差异 | 需要可信网格、材质、燃料映射、跨 LOD 稳定 ID、更多参数和验证；目前没有这些依据 | 暂缓，不能借视觉细节假称已实现 |

## 当前源码事实

- [`FireProfile`](../../../modules/naval_simulation/combat/fire_profile.gd) 为 `ship-fire-r1`：固定 `1/60s`，全船热量上限 100、燃料上限 72 秒；普通／蒺藜灵感载荷分别增加 18／36 燃料秒。均为游戏参数。
- [`FireControl`](../../../modules/naval_simulation/combat/fire_control.gd) 严格接受十字段字典。唯一热量、燃料、整数伤亡余量、损管队、120 tick 转岗、准备份与工作余量均属全船；`step` 分段处理热灭、热量封顶、燃料和工作预算耗尽，再返回一份统一烧损。
- [`Encounter`](../../../modules/naval_simulation/encounter.gd) 在 `_fixed_tick` 中先真实弹体 Sweep，再 `_advance_fire`、最后终局；火攻命中目前虽有真实世界坐标，但 `Fire.ignite` 不接收命中区。普通 `hit` 与火攻事件分开，DOT 不进入普通货损分支。辅助 launcher 现有代价为 4 人、2 秒操作、12 秒共用冷却。
- [`ShipFireView`](../../../game/presentation/combat/ship_fire_view.gd) 只读有效 `fireControl.heat`，每船只有一个火点；中央位置来自 [`ShipView.source_destruction_anchor`](../../../game/presentation/ships/ship_view.gd)。它不是三个区的真实锚点。
- [`DeckSupport`](../../../game/presentation/crew/deck_stations.gd) 可从真实甲板三角面采样支撑高度与法线；[`原实验`](../../../game/research/demos/ship_fire_control_experiment.gd) 已有固定 60Hz、seed 1661、无人／有人对照和固定镜头。扩展该实验即可，无需新 Demo 或目录项。

本轮只读观察。CodeGraph 返回本仓库未建索引，以上使用 RTK 源码回查；没有运行 Godot、GPU 或性能检查。Godot 官方也区分固定物理 tick 与渲染帧，不能让传播计时随渲染次数变化；固定时间步本身不等于证明跨平台浮点逐位一致。[官方说明](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html)

## 最小权威状态与兼容边界

推荐新候选版本 `ship-fire-r2-zones`。**不向 r1 十字段字典塞入新键，不放宽 `FireControl.valid`，不把三份 r1 拼在一起。** 新纯模块为 `res://modules/naval_simulation/combat/fire_spread.gd`，仅允许独立核与同一实验验证；本轮不接 Encounter 或 Campaign。未来正式 opt-in 必须另过接线门槛。原无扩展、原 r1、旧三弹药与旧 RNG／命令顺序保持原路径。

```text
version: "ship-fire-r2-zones"
heatByZone: [bow, mid, stern]       # 3 个非负有限热量份额；总和 H ≤ 100
exposureTicks: [bow, mid, stern]    # 冷区连续受邻区威胁的接受 tick，整数 0..360
fuelSeconds: 0..72                 # 全船唯一剩余燃烧时间预算
wetness: 0..1                      # 本候选仍用全船单一湿润度
crewDamageCarry: [0,1)             # 全船唯一整数伤亡余量
assignedFirefighters, pendingFirefighters: 整数 0..128
transferTicks: 整数 0..120
supplies: 整数 0..600
workCarry: [0,2) 人秒              # supplies==0 时必须为 0
```

这是严格 **11 个顶层字段**：r1 去掉 `heat`，增加 `heatByZone` 和 `exposureTicks`；没有 `autoEnabled`。全船热量 `H=sum(heatByZone)`、燃烧区数、UI 状态和“危险”均为派生值，不另存第二份可推进的 `heat`。

拟定 API 为 `initial(supplies=0)`、`valid(state)`、`summary(state)`、`ignite(state,payload,wetness,zone)`、`assign(state,crew,able)`、`reserved_crew(state,able)` 和 `step(state,context)`。`zone` 仅允许字符串 `bow/mid/stern`；context 与 r1 完全一致。`summary` 返回分离的严格 r1 十字段，版本为 `ship-fire-r1`、heat 为三区之和。`step` 每次 **恰好调用一次** `Fire.step(summary(state),context)`，返回原结果全部烧损／工作／人员信息，并将 `state` 替换为 r2；另附 `spreadEvents:Array`。失败仍原子拒绝，无烧损、扣费或传播。摘要只是当次派生输入，不持久化。

准备份、伤亡余量、燃料和人员账绝不分区复制。初始 24 份仍只有一次 24 份；这是当前火攻交锋训练初态，不能扩展成生涯免费赠送。r1 档案维持 r1；旧档缺扩展维持缺失。r2 的 Campaign、Bridge、SaveCodec 往返须先写严格独立分支并验证，再允许生涯 opt-in；30 号已冻结的 r1 合同仍有效。不得自动将任意旧热量拆三份，或为旧正火值猜燃料历史。

## 真实命中与渐进传播

**命中区取自权威 Sweep，不取镜头、粒子或当前 GLB。** [`projectiles.gd`](../../../modules/naval_simulation/combat/projectiles.gd) 的移动盒 Sweep 按旋转切片，并用该片中点 heading 做 slab 检查。候选需要一个兼容的详细 contact helper，返回获胜 TOI 及同一碰撞坐标系的纵向坐标；保留原 `sweep_moving_box` 返回 TOI 的 API 和行为。只用期末 heading 再分类，在转向时可能错区，不能作为正确实现。

设该船权威碰撞长度为 `L` 米，局部纵向 `u` 的正向为船首，分区固定为：`u < -L/6` 属船尾；`-L/6 <= u <= L/6` 属船中；`u > L/6` 属船首。接缝属于船中，阈值无需浮点随机打散。当前碰撞盒包含较高的帆装包围盒；首版把这种命中按纵向投影至对应甲板区，必须明示是游戏映射，不能称逐帆材质点燃。

真实命中只向该区增加 `28*(1-.60*wetness)` 热量，受全船 `100-H` 剩余空间限制；只向全船燃料增加对应 `18/36*(1-.40*wetness)` 秒，封顶 72。未命中、先触水、失效弹体和普通炮击不产生新的候选火区。命中即使处于总热量上限，也仍按既有有限燃料上限接受真实载荷；不返还已消耗弹药。

以下 **24／360／12 为预先提出的实验候选，未调平衡**：

1. 仅本步起点冷区，即 `heatByZone[j]==0`，可积累 `exposureTicks[j]`。至少一个相同邻区在本接受步起点与 r1 推进后均有热量 `>=24`，且剩余燃料仍正，计数加 1；条件失去即归零。采用端点资格的粗粒度有限 tick 近似，不额外构建舱室内连续热学。已有活火区计数恒为 0。
2. 达到 360 tick，即连续 6 接受秒，在本 tick 末尝试传播；从合格邻区中取热量最高者，平手按固定首／中／尾顺序。该源区必须至少保留 12 热量。
3. 从源区转移 12 热量到该冷区；源减 12，目标加 12，**全船总热量和剩余燃料均不增加**。冷区开始成为真实热源，后续也能被扑灭或继续向邻区传播。
4. 本 tick 新点燃的区下一 tick 才可充当传播源。同 tick 多个目标先冻结候选，再按固定首／中／尾顺序提交；每次重新检查源区可转出的余额。失败目标清零计数，不能负热量或留下可重复兑换的传播票据。

这样，无人处理的尾部火源可以先延至船中；更长的有限燃烧才可能继续延至船首。中部火源可同时威胁两端，代价仍来自同一份热量。首轮空间扩展刻意不附加伤害倍率；局部明火被压灭会实际中断其传播条件，空间状态并非粒子数量推算。实际时刻依赖后述降温与湿润，必须由日志测定，不能把以上叙述写成已测时间表。

传播不补燃料、燃料耗尽令三区热量与计数归零；`H==0` 不因残余燃料自动复燃。没有新命中时，即使发生反复局部复燃，传播也只能发生在最多 72 接受秒的剩余预算内，不形成无限链。热灭可保留未燃燃料，与 r1 一致；它不是自动起火许可证。

## 复用一支损管队、一个工作预算、一份 DOT

H5 复用现有派 4 人按钮和 r1 的 assign、reserved_crew 与自动热灭返回：120 个完整转岗 tick 零工作，第 121 步才工作；同目标重复命令不重启转岗，途中／返回仍占人。原人数校验、伤亡裁剪、缺人拒绝及有限准备份规则不变。独立研究控件仍可比较 0/2/4/8 人。H5 不实现长期自动政策、1 人自动补位或跨火情自动重派；一次火情内不要求玩家逐区救火。

本候选是全船协同损管的粗粒度抽象，不新增局部人员路径、三队人员或独立舱室物理。设 `N` 为 r1 本步实际工作人数，`H=sum(h_i)`；唯一 r1 内核保持：

```text
全船自然升温 G = 2*(1+.75*flammableLoad)       热量/秒，整船只算一次
全船湿润降温 W = 6*wetness                   热量/秒，整船只算一次
队伍降温 C = 1.5*N                          热量/秒，整队只算一次
全船变化率 = G-W-C，受 H∈[0,100] 与有限燃料限制
全船工作预算 B = 2*supplies-workCarry         人秒，整船只算一次
```

先记 `H_before`，调用一次 r1 step 得 `H_after`，再分配唯一差值：正差均分给本步起点已经燃烧的区；负差从最热区移除，不足再取下一热区，平手按首／中／尾。允许极小浮点余量修正，但全船总和须与 r1 摘要一致，不靠多调一次 r1 补差。冷区不凭正差自燃。`H_after==0` 或燃料耗尽时三区和计数全部归零，随后才检查上述传播资格。`ignite` 也先调用旧点燃核，将其接受的热量差仅放入真实命中区，并清该区计数。

本步直接返回 r1 对 `A=∫H(t)dt` 的一次船体、帆和人员烧损、工作、储备消耗及熄灭结果；不重算这些量。未来接线也只允许 Encounter 应用一次。不能对每区分别传入整船 maxHull/maxCrew 并调用旧 `Fire.step`，也不能让 Campaign 或 VFX 再结算一轮。

实际工作、每 2 人秒一准备份、半 tick 枯竭、热灭自动返回均由原 r1 实现决定。准备份耗尽不等于熄灭，也不新增自动撤回政策。灭火不恢复 hull、sail 或 crew；没有火时不收费。损管仍与辅助投送、炮组、登船争用同一 roster，32 号人 tick 账若启用仍只计一支队，不计三区三份岗位。

## 可读反馈与实际甲板锚点

普通镜头需要看懂四件事：哪里着火、正在延到哪里、队伍是否到位、准备份是否耗尽。建议保留一行状态，例如“船尾起火 · 救火队赶往中 · 储备 21”；三区简图只显示首／中／尾亮灭与威胁，不要求点击。停火后明火关闭，余烟按原有限寿命衰减；暂停冻结权威热量、传播计数、工作账和出生时刻，转镜头只刷新位置。

视图须读取 r2 的每区真实热量。每个区在模型配置时，从实际 DeckSupport 支撑面采样该纵向区间内可用位置，保存模型局部锚点；随原船模 transform 更新到世界空间。船首方向与 ShipView 的模型正 Z 对应关系必须用船型夹具验证；不可将三个世界坐标硬编码到海面。甲板高低不一时各自取真实支撑 y；缺支持则明确报告该区无锚点，不以中央点平移或假 y 掩盖。

火焰贴当前真实区锚点，旧烟粒子留世界空间，入水不画明火。当前 `MAX_LIVE_FIRES=16` 是活火船预算；三区不能悄悄把总粒子／sprite 成本扩三倍。候选维持有界全局池，最多 16 艘、48 个区锚点，按区热量分享既有总发射预算；降画质不能改变权威传播。可见船员若仍无扑救专用动作，应继续如实说明，不能把占人数字称为已验证提桶动画。

## 预先接受项与平衡实验

下表覆盖整个候选；纯核、同 Demo 受控点燃与连续图形回执见37号记录，真实命中／持久化等仍不能据此升级。原实验已增加r1/r2选择与首中尾受控点燃，沿用同课题与固定种子、镜头和宿主生命周期；不是实弹命中。旧结果保留，不覆盖失败，不按结果回改接受阈值。

| 范围 | 候选必须满足的条件 |
| --- | --- |
| 兼容与数据 | 无扩展旧 encounter 与 r1 oracle 不变；r1 拒绝 r2 键；r2 严格拒绝缺键、未知键、越界数组、NaN/Inf、数字 bool、分数计数；JSON整数 float 的恢复规则与原核一致 |
| 命中 | 静止／平移／转向下，首中尾和 ±L/6 边界分类明确；水面先 TOI 不点燃；同一真实命中只增加一次热量及燃料；普通 hit 的货损次数不变 |

| 人员与准备份 | 同一 roster 不重分给 launcher／炮／登船；工作≤真实到岗人秒且≤初始可用 B；储备不负、无火不扣费、枯竭半 tick 正确；返回期间仍占人；冷自动政策不占岗 |
| 一键体验 | 本次火情派现有 4 人后无需选区或连续点火点；不足 4 人沿旧命令反馈；不测试尚未实现的永久自动政策、跨火情重派或新 UI |
| 暂停与生命周期 | 重复时间、暂停、低渲染帧率不增加传播 tick、工作或出生；固定接受输入重置一致；epoch／读档恢复计数；离场释放，无旧火跨新局 |
| 真实 GPU | 首／中／尾分别受控起火并连续蔓延；扑救阻断、耗尽后仍燃、余烟、入水和转镜头可读；原帧绑定 tick 与 snapshot。静态图不能证明蔓延 |
