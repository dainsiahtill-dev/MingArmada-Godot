# 航行目标行裁切修复

真实开局 GPU 输入诊断中，玩家离港后左右舷状态出现，左上 HUD 的当前目标与“查看”按钮被滚动区域底缘裁掉；原采集器把离开滚动区的内容排除在 overflow 候选之外，因此过去的零 overflow 不能证明目标首屏可见。

将目标行移到标题下方；桌面 HUD 非手册上限从 270 调整到 310 像素，窄屏从 150 调整到 156 像素，并以底部操船栏的位置约束窗口高度。保留滚动与原有按钮行为，状态更新不强制抢走用户的滚动位置。

新增真实 Mingqi runtime 的港内和离港布局/输入测试，覆盖 1600×900、1280×720、320×480、当前项目较长目标、无目标、手册和手动滚动；[结果 88/0](../../migration/evidence/opening-story/gameplay-current-20261027/objective-hud-full-green-01.log)，相关布局、场景、操船和剧情测试亦通过。原问题和长目标中间失败日志保留。

GPU 复查从真实 MainScene 以 viewport 鼠标事件进入并离港：[离港诊断](../../migration/evidence/opening-story/gameplay-current-20261027/departure-gpu-hud-fix-02/capture-result.json) 有 9 图，日志 115/0（JSON 先于最终读回检查写入，故记为 114/0）；[航程 UI 组](evidence/hud-objective-mingqi-20261027/capture-result.json)有 21 图、265/0。独立核对截图和记录中的源码哈希。1280 与 1600 离港图里，目标、查看、两舷状态和航程时限完整，中央海面和底部指令栏可见；320 港内图的目标与查看完整，但日志、HUD 和底栏几乎占满高度，其他信息需滚动，窄屏航行视野仍需优化。

证据是 GPU 画面与 Godot viewport 注入，不是操作系统人工鼠标、完整持续航行或 FPS。离港截图阶段冻结正常 `_process` 后手动推进物理步，因此首张海上图 HUD 时间未同步，打开日志刷新后的图才反映新时间；不能以此认定正式连续游戏存在显示延迟。用户原存档与首航前 12 项基线在本次离港 GPU 诊断之后核对无差异，但该基线并非紧贴 GPU 启动的独立记录；后续航程 UI 组自身另外记录了原 12 项存档运行前后一致。
