# 首航靠港节奏：只读根因审计

2026-10-12。生产源码、既有测试、真实旅程、存档和图形均未修改；没有启动 GPU 窗口、推进物理时间或重跑全套测试。CodeGraph 本会话已确认无索引，使用获准的 RTK 源码检索。

## 结论

长等待的主要可证原因是**港内自动避碰没有合适的恢复决策**。真实粮船甲已经进入距金门约 26–28m 的安全水域，却被当前航向前方的背景商船触发停车。自动驾驶只尝试目的地方向加减 60°；乙船、迎风限制及后期浅水让两个候选均失败，于是反复收帆、停止转向恢复，靠极小的真实残余运动等待。

这不是保守规划圆盘拒绝起点，也不是进入 18m 后正常收帆；不应归为性能问题。确实有局部碰撞风险，所以也不能删掉避碰、忽略船只、扩大卸货范围或直接转到目标。**750s 记录存在代码未尝试的可行目的地方向；450s 记录则证明无条件直转会碰船。**

本审计复核真实帧的当前几何和原有代码分支，没有完整恢复每个历史 tick 的 route cache、tack、舵帆、yaw 或接触事件。它支持上述长期阻塞根因，不声称已完成逐 tick 控制器回放或修复航程。

## 同一正式 HeightField 的静态隔离结果

[探针源码](../../../../build/diagnostics/port-approach-pacing-probe.gd)读取不可变实际帧，调用当前未改的 `Planner.plan`、`Encounter._wet_hull`、`_ship_ahead` 和 `_feasible`。使用 `mingqi_geography.json` 和正式 `reference_geography.gd` 配置；没有 flat 地形替代。

适配器仅返回所记录的完整精度位置、速度、航向。尺寸来自同一真实船的 catalog；甲船未交货前载 20 粮，正确吃水为 **1.6m**，不能误用最终卸货后的 1.2m。标量距离和圆盘半径使用 float64，避免本构建 Vector2 的 float32 舍入。

[完整静态输出](../../../../build/diagnostics/port-approach-pacing-probe.json)覆盖 **41 帧，300–1500s**：

- 41/41 新规划成功，均为到记录目标的一段直线；起点和终点转向圆盘全部湿，138 个采样中干点为 0。圆盘半径为 `hypot(36,10)/2+8 = 26.68154m`。
- 41/41 真实朝向的九点船体湿度通过。420s 以后的当前船体最高地形为 -8.0m，低于 -1.6m 吃水边界。
- 420–1470s 的 **36 个记录帧**全部 `shipAhead=true`，目的地方向 ±60° 两个候选全部 `feasible=false`。500s 以后没有出现起点/终点 `unsafe-endpoint`。
- 540s 原航向前方背景商船距甲船 **30.02413m**，航向角差 **0.431235rad**，落在现有 54m、0.6rad 阻塞锥内。+60° 候选被乙船挡住（28.27563m、角差 0.134318）；-60° 候选被背景商船挡住（30.02413m、角差 0.114094）。两候选风与 0/15/30/45m 湿船体均安全，拒绝原因是船只。
- 750s 起 +60° 还违反 50° 风向安全区；-60° 后续轨迹出现真实浅水/陆地。不能绕过这些拒绝。

源码路径：

- `modules/naval_simulation/encounter.gd:623–633`：当前朝向前船锥与候选风/船/0、15、30、45m 湿船体检查。
- `encounter.gd:634–651`：规划起点/目标、缓存、失败停车。此次静态帧规划全成功，区别于此前乙船漂出港后的 `unsafe-endpoint` 问题。
- `encounter.gd:655–661`：当前航向被阻塞后只尝试 `desired+PI/3` 和 `desired-PI/3`，两者失败即 `blocked=true`，把 desired 改回当前 heading。
- `encounter.gd:667–680`：目标外侧允许接近，`blocked` 却立即把帆收为 0；低速转向恢复也对 blocked 返回空请求。它没有港内排队优先级、移动船障碍重规划或长期停滞恢复分支。
- `game/runtime/near_field_bridge.gd:51–62`：中间业务航点在 18m 内推进，最后港点仍保留。甲船 330s 起记录的导航就是金门港点，不是中间航点没交接。
- `game/domain/mingqi/campaign.gd:497–509`：卸货仍要求真实距港 ≤25m、真实速度 ≤0.75m/s；此次甲船大多停在范围外，业务拒绝是正确的。

## 存在更合适的方向，但静态可行不等于动态安全

750s 真正目的地朝向是 **1.381681771242557rad**。它通过原 `_feasible`：风角差 1.75991rad，前船列表为空，0/15/30/45m 的四组九点湿船体全部通过。当前航向却被背景商船挡住（39.65180m、角差 0.599182rad）。两个 ±60° 分支都被拒绝，所以当前代码不尝试这个目的地方向。

另一个独立的纯 Python 静态 [SAT 检查](../../../../build/diagnostics/port-approach-collision-audit.py) / [输出](../../../../build/diagnostics/port-approach-collision-audit.json)使用当前 `Encounter._extent` 与分离轴公式，对八个真实帧作 1° 转动采样、1m 直线路径采样：

- 750s 在原位置从 0.081843rad 转到真实目的地朝向，全部所采样姿态无其他存活船矩形重叠；沿该方向到真实港点约 27.4m 的所采样位置也没有重叠。第一次潜在快船重叠是 **44m**，已越过港点，不是到港前实际阻塞。
- **450s 反例**：从当时航向仅开始转约 1° 就与背景商船矩形产生重叠。此时 `desired` 方向可能通过现有前船锥，但不能证明旋转过程安全。禁止仅增加方向并信任锥判定、禁止无条件忽略背景船。
- 静态转动/轨迹采样没有考虑下一时刻相对速度、未来船位、连续碰撞、制动距离或波浪运动。不能把结果标为动态安全证明，不能据此发送真实导航命令。

## 最小下一迭代建议（未实现）

优先修正**低速港口末段的候选选择**，不要先调快全海域航速：在现有 `routePlanning && referenceHandling` 的低速、25–55m 自动靠港场景，当前航向被堵时，先考虑真正 `desired`；只有真实 native 连续旋转及制动至目标范围的船体湿度、船只相对运动扫掠、未来时间间隔防撞均通过才允许，失败继续原 ±60°/停车行为。禁止将上述静态例子当成最终门禁。

必须保留：

1. 真实船尺寸、满载吃水、整个转动/行进船体湿度、浅水与陆地拒绝；任何船的连续碰撞与现有物理接触处理。
2. **25m、≤0.75m/s 真实卸货**，真实到达收据与货物/港口库存结算；无 teleport、状态修补、提前卸粮或奖励。
3. 当前手动输入、实际订单、explicit 控制序列、船员/损伤/俘获/禁动/服务锁门禁；玩家的旗舰与护航命令不能被自动靠港抢走。
4. `routePlanning=false`、`referenceHandling=false` 旧路径、一般远海航行和18m中间航点语义不变。遇敌不能借靠港恢复绕过安全制动或战斗。
5. 后续真实首航/补给航程应记录 route、blocked reason、候选拒绝原因、舵帆、局部速度与接触收据；验证玩家在敌船已击败后无需十几分钟无决策等待，再评估手感。静态探针不替代实际航行与真人体验。

后续 UI 建议：期限/ETA 从绝对模拟秒数改为真实剩余时长，并明确补给船“已装载、可出港/仍未就绪”。例如现有期限 2724s、HUD 1524.2s 容易让玩家自行相减。此项来自 root 的真实 UI 验收，本审计没有修改界面。
